# 本地大模型部署调优指南

**无 NVLink 多卡场景的配置决策库。**

不是原理科普，是决策依据 —— 每条结论都标注它的来源和适用条件。

---

## 为什么需要这个项目

国内绝大多数本地推理部署跑在**没有 NVLink 的机器**上：RTX 4090 / 5090、RTX PRO 6000、各代 PCIe 版计算卡，通过 PCIe 5.0 x16 或 PCIe Switch 互联。

但主流推理框架的文档、调优建议和默认配置，几乎都建立在"卡间有高速互联"这个假设上。结果就是：

- 同样 4 张卡，有人跑出 1400 tok/s，有人只有 600 tok/s，差别全在配置
- 中文资料里"讲原理"的文章很多，但**参数建议互相矛盾，且几乎都不说明测试条件**
- 你无法判断一条建议到底适不适用于你的机器

这个项目要补的是另一半：**把结论和它的适用条件绑在一起。**

## 快速决策表

先回答最高频的六个问题。

| 你的情况 | 建议 | 依据 |
|---|---|---|
| 模型（含 KV）能塞进单卡 | **多副本（replicas）优先于张量并行** | 实测 + 可推导 |
| 模型必须切，且卡在同一 PCIe Switch 下 | TP = 该 Switch 下的卡数 | 可推导 |
| 卡跨 PCIe Switch 或跨 CPU Socket | **TP 不要跨过去**，改用 TP×PP 组合 | 可推导 |
| 想要更长上下文 | 先降 KV 精度 / 加卡，DCP 在 PCIe 上收益有限 | 实测 + 可推导 |
| 想用推测解码提速 | **draft 长度不是越大越好**，从 2–3 开始测 | 实测 |
| 量化掉点明显 | 检查 MoE 路由层是否被一起量化了 | 实测 |

## 数据可信度分级

本项目所有结论都带依据标记：

| 标记 | 含义 |
|---|---|
| **实测** | 有公开可查的测量数据，附硬件、时钟、软件版本与客户端命令 |
| **可推导** | 由硬件规格或框架机制直接推导，不依赖具体某次测量 |
| **待测** | 方向明确但缺公开数据；本项目给出测量方法，等你用自己机器填 |

**我们不做的事：不给没有依据的具体数字。** 空格比编造填得更满有价值。

## 核心结论速览

以下六条是当前最有把握的判断，展开见各章节。

1. **能塞进单卡，就别做张量并行。** 两个独立副本之间零通信，吞吐直接线性叠加；而 TP 每层都要 all-reduce，在 PCIe 上这个代价会吃掉大部分收益。
2. **TP 的边界是 PCIe Switch，不是显卡数量。** 跨 Switch 的通信要走 CPU 内存，延迟骤增。四张卡插在两个 Switch 上时，TP=4 往往不如 TP=2 × PP=2，甚至不如两个 TP=2 副本。
3. **PCIe 拓扑下应优先 one-shot all-reduce。** 帧同步式的 two-shot 在高速互联上更优，但它的优势建立在带宽充裕的前提上——PCIe 恰好相反。
4. **推测解码的收益受带宽约束。** draft 越长，单次验证失败浪费的计算越多，而草稿模型本身还要占用带宽。在 PCIe 机器上，3 个 draft token 的方案可能明显快于 7 个。
5. **量化要优先保护路由层。** MoE 模型里，专家权重可以激进量化，但路由器选错专家会直接毁掉输出。把 router 保持在更高精度，代价远小于收益。
6. **同一台机器，配置差异可以造成 2 倍以上的吞吐差距。** 这不是玄学，是每一个参数都在和你的实际拓扑对齐。

## 怎么用这个项目

**如果你要部署一台新机器**：从 [01 硬件与拓扑](docs/01-hardware.md) 开始，先跑一次 `nvidia-smi topo -m`，再去 [配置配方](recipes/) 找最接近你硬件的配置。

**如果你已经有机器但吞吐不理想**：直接用[配置生成器](tools/config-generator.html)，对比它给出的参数和你现在的差异。

**如果你想贡献数据**：见 [CONTRIBUTING.md](CONTRIBUTING.md)。数据表格已经做好，缺的就是真实机器的测量值。
