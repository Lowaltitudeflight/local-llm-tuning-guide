# 同样 4 张卡，有人跑 1400 tok/s，有人只有 600 —— 无 NVLink 多卡部署的 6 条硬结论

> 国内绝大多数本地推理部署跑在没有 NVLink 的机器上：4090 / 5090、RTX PRO 6000、各代 PCIe 计算卡。
> 但主流推理框架的文档、默认参数和"最佳实践"，几乎全是为 NVLink 集群写的。
> 这篇文章把"什么配置适用什么机器"讲清楚，**每条结论都标注来源和适用条件**。

---

## 一、先看一个让人沉默的对比

同一批硬件、同一个模型、同一个框架版本：

**4 × RTX 3090（无 NVLink）· AWQ 量化 Qwen3-35B-A3B · vLLM · 8K 上下文 · 128 并发**

| 配置 | 聚合吞吐 |
|---|---|
| 双实例，各 TP=2（两份独立副本） | **1437 tok/s** |
| 单实例，TP=4（四卡张量并行） | **610 tok/s** |

**2.4 倍差距。** 不是换了卡，不是换了模型，只是并行配置不同。

如果你在自己的机器上跑出来的数字低于预期，先别急着怀疑显卡、怀疑框架、怀疑量化——**大概率是配置和你的实际拓扑没有对齐**。

> 说明：这是单一条件下的单次测量（消费级卡、8K 上下文、特定模型）。方向性结论可迁移——"副本优于跨卡切分"——但具体数字不适用于其他硬件或模型。

## 二、为什么框架的默认配置在你的机器上会失效

根因只有一个字：**带宽**。

| 互联方式 | 典型双向带宽 | 出现场景 |
|---|---|---|
| PCIe 4.0 x16 | ~64 GB/s | 上代平台、消费级主板 |
| PCIe 5.0 x16 | ~128 GB/s | 当前主流工作站与服务器 |
| NVLink 3（A100） | ~600 GB/s | A100 SXM |
| NVLink 4（H100） | ~900 GB/s | H100 SXM |
| NVLink 5（B200） | ~1800 GB/s | B200 / GB200 |

**PCIe 与 NVLink 差 7～14 倍。**

这不是一个可以忽略的量级。张量并行（TP）的每一步都要做 all-reduce——也就是卡与卡之间交换数据。当卡间带宽差距是 7 倍时，**"在 NVLink 上最优"的配置搬到 PCIe 上，往往就是最差的那一个**。

所以你会看到这些现象：

- 照抄某篇"4 卡部署"教程，参数一字不改，吞吐只有别人一半
- 中文资料里"讲原理"的文章很多，但参数建议互相矛盾，而且**几乎都不说明测试条件**
- 你根本没法判断一条建议到底适不适用于你的机器

## 三、动手调参之前，先跑这一条命令

**这是本文最重要的一段。** 在你改任何参数之前，先搞清楚你的卡到底是怎么连的：

```bash
nvidia-smi topo -m
```

输出是一张矩阵，交叉点就是两张卡之间的**连接类型**：

```
        GPU0    GPU1    GPU2    GPU3    CPU Affinity    NUMA Affinity
GPU0     X      PIX     PXB     SYS     0-31            0
GPU1    PIX      X      PXB     SYS     0-31            0
GPU2    PXB     PXB      X      SYS     0-31            0
GPU3    SYS     SYS     SYS      X      32-63           1
```

标记含义，按速度从高到低：

| 标记 | 含义 | 相对速度 |
|---|---|---|
| `NV#` | NVLink，数字是链路数 | 最快 |
| `PIX` | 经过**单个** PCIe Switch | 快 |
| `PXB` | 经过**多个** PCIe Switch | 中 |
| `PHB` | 经过 PCIe Host Bridge（CPU 引出） | 慢 |
| `SYS` | 经过 CPU 间互连（**跨 NUMA**） | 最慢 |

上面这个例子里：GPU0/1/2 在同一组 PCIe Switch 下（`PIX`/`PXB`），而 GPU3 在另一颗 CPU 上（`SYS`）。

**结论直接就有了**：`TP=4` 会让每一步 all-reduce 都撞上最慢的那条链路（要出 CPU、过 UPI、再进另一颗 CPU），应该考虑 `TP=3`（全部留在 Switch 内）或 `TP=2 × PP=2`。

这就是"先看拓扑再调参"的意义——**拓扑决定了你能选什么，而不是反过来。**

## 四、6 条逆着"常识"的结论

### 1. 能塞进单卡，就别做张量并行

如果模型（含目标上下文的 KV 缓存）能放进一张卡，那么**多开几个独立副本**几乎总是比 TP 快：

- 副本之间**零通信**
- 吞吐随副本数**线性增长**
- 一个副本挂了，其他还在服务

上面那个 1437 vs 610 就是这条结论的直接证据。`TP=4` 每层都要 all-reduce，在 PCIe 上这个代价会抵消掉大部分收益；而两个 `TP=2` 副本只有 2 卡间通信，各跑各的，加在一起反而更快。

**依据：实测 + 可推导**

---

### 2. TP 的边界是 PCIe Switch，不是显卡数量

模型放不进单卡、必须切的时候，判断规则是：

```
能否放进同一 PCIe Switch 下的卡数？
├─ 能  → TP = 该 Switch 下的卡数
└─ 不能 → 用 TP × PP 组合，让 TP 留在 Switch 内部，PP 跨越 Switch
```

**为什么？** TP 的通信发生在**每一层内部**，而 PP（流水线并行）只在**段的边界**传激活值。层数越深，TP 的累计通信代价越大。

从第三节那个示例拓扑出发：

| 配置 | 评价 |
|---|---|
| `TP=4` | ❌ 每一步 all-reduce 都撞上最慢链路 |
| `TP=3` | ✅ 全部留在 Switch 内 |
| `TP=2 × PP=2` | ✅ TP 留在快链路，PP 只在段边界传激活 |
| 两个 `TP=2` 副本 | ✅ 前提是模型能放进 2 卡 |

**依据：可推导**

---

### 3. PCIe 拓扑下应优先 one-shot all-reduce

all-reduce 有两种实现，取舍核心是**当前是延迟主导还是带宽主导**：

| | 两阶段（reduce-scatter + all-gather） | 单步（one-shot） |
|---|---|---|
| 通信总量 | 与 rank 数近似无关 | 随 rank 数**线性上升** |
| 同步次数 | 两次 | 一次 |
| 优势场景 | **大消息**、带宽受限 | **小消息**、延迟受限 |

对应到推理的两个阶段：

- **Prefill**：一次处理几千个 token，消息很大 → 带宽主导 → 两阶段仍有价值
- **Decode**：每步只处理很少的 token，消息很小但同步极频繁 → **延迟主导** → 单步更优

所以正确的问法不是"哪个算法更好"，而是"**我这个阶段的消息有多大**"。

公开的 PCIe 优化实践（Local Inference Lab 的 GLM-5.3-Flash 配置）里有两点值得抄：一是**默认关闭 two-shot**，走单步路径；二是提供了 `VLLM_PCIE_TWOSHOT_ALLREDUCE_MAX_SIZE` 这类**按消息大小切换的阈值**参数。

第二点比第一点更有启发：**结论不是一个算法，而是一个阈值。**

**依据：实测 + 可推导**

---

### 4. 推测解码：draft 越长，反而可能越慢

这条最反直觉，也最值得单独拎出来。

**4 × RTX PRO 6000 Max-Q（无 NVLink）· TP4 · NVFP4 量化 MoE 模型 · 32 并发槽位 · FP8 KV 缓存**

| 模式 | draft token 数 | C1 单并发 | C8 聚合 | 32K prefill |
|---|---|---|---|---|
| MTP3 | 3 | **281.3 tok/s** | **897.6 tok/s** | 13,816 tok/s |
| DFlash2 K7 | 7 | 229.0 tok/s | 702.6 tok/s | 13,955 tok/s |

**draft 从 3 增加到 7，单并发输出反而下降 18.6%，聚合下降 21.7%。**

而 prefill 两者几乎相同（13,816 vs 13,955，差 1%）——符合预期，推测解码只作用于解码阶段。

**为什么猜得多反而慢？**

1. **草稿模型要占显存**——挤占了 KV 缓存空间；额外权重访问还挤占了本就稀缺的带宽
2. **猜错浪费更大**——接受率不变时，更长的 draft 意味着更多被丢弃的计算
3. **跨卡同步要抢链路**——无 NVLink 的机器上，草稿与验证的同步要和主模型的 all-reduce 争同一条 PCIe

> ⚠️ **数据波动提示**：该来源自己声明，另做的一组五次 C1 检查测得 MTP3 为 265.7–277.0 tok/s、DFlash2 为 212.9–225.2 tok/s。存在约 ±5% 的启动间波动，**不要拿它做精细的版本比较**。

**实践建议**：首次配置**从 draft = 2–3 开始**；无 NVLink 多卡时保持 3 左右；想提速时先看 KV 精度和并行配置，**最后才考虑挂独立草稿模型**。

**依据：实测**

---

### 5. 量化要优先保护路由层

MoE 模型有个特殊风险：**路由器选错专家，输出会被彻底带偏**，而且这个错误不会被权重量化的"平均误差"掩盖——它是**离散的、跳变式的**。

公开的量化报告（针对 GLM-5.3-Flash）比较了 W4A4 / W4A8 / W4A16 三种激活精度和 FP32 router 权重的影响，关注指标是 **greedy checksum 稳定性**（相同输入是否稳定产生相同输出）。

结论指向：**激活量化越激进，MoE 的输出确定性越难保证；把路由器权重保持在更高精度，是性价比很高的一步。**

优先级：

| 优先级 | 做法 |
|---|---|
| 1 | 路由器权重保持 FP32 或至少 BF16 |
| 2 | 专家权重可以更激进量化 |
| 3 | 激活精度从 A16 起步，确认无损后再降 |

**一个容易被忽略的检查项：输出确定性。** 同一 prompt 用 greedy 解码跑两次，输出应当**完全一致**。如果量化后不一致了，说明数值路径出了问题——这在 MoE 上尤其常见。

**依据：实测**

---

### 6. 同一台机器，配置差异可以造成 2 倍以上的吞吐差距

这不是玄学。**每一个参数都在和你的实际拓扑对齐**——对齐了，性能就出来了；没对齐，一半算力就在通信上排队。

诊断顺序，不要跳步：

```
1. nvidia-smi topo -m          ← 先看卡怎么连的
2. 看并发数                     ← 通信开销能否被批处理摊薄
3. 最后才怀疑框架/量化           ← 前两步没做,换什么框架都白搭
```

## 五、直接能用的配置

以下是一个 4 × 96GB PCIe 机器的起点配置。**注意：先用第三节的方法看你的拓扑，再决定用 A 还是 B。**

### 情况 A：四卡在同一 PCIe Switch 组（TP=4）

```bash
vllm serve <your-model> \
  --tensor-parallel-size 4 \
  --pipeline-parallel-size 1 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --max-num-seqs 32 \
  --max-num-batched-tokens 4096 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --host 0.0.0.0 --port 8000
```

### 情况 B：四卡分属两个 Switch（TP=2 × PP=2）

```bash
vllm serve <your-model> \
  --tensor-parallel-size 2 \
  --pipeline-parallel-size 2 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --max-num-seqs 32 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --host 0.0.0.0 --port 8000
```

不需要额外参数——让 PP 承担跨 Switch 的通信，它只在层边界传激活值，代价远小于 TP 的逐层 all-reduce。

**两个容易出错的设置：**

- `--gpu-memory-utilization` **不要一上手就 0.95**，突发峰值容易 OOM；0.90 起步。
- 如果你的卡是低功耗版（Max-Q 类，约 300W），**功耗墙可能先于显存成为瓶颈**，测量记录里要标明功耗上限。

## 六、一个必须会算的公式：KV 缓存占用多少显存

很多人问"我的模型能支持多长上下文"，其实这可以**精确估算，不需要试错**：

```
每 token 的 KV 字节数 = 2 × 层数 × KV头数 × head_dim × 每元素字节数
                        ↑
                    K 和 V 各一份
```

**注意是 `KV头数` 而不是注意力头数**——采用 GQA/MQA 的模型，KV 头数远小于注意力头数，这是它省显存的关键。

**算例**：64 层、8 个 KV 头、head_dim = 128

| KV 精度 | 每 token | 32K 上下文 | 128K 上下文 | 1M 上下文 |
|---|---|---|---|---|
| BF16（2B） | 256 KB | 8 GB | 32 GB | 256 GB |
| FP8（1B） | 128 KB | 4 GB | 16 GB | 128 GB |

看最后一行：**即使 KV 压到 FP8，100 万 token 上下文仍需 128 GB**——超过了一张 96GB 的卡。

这就是**"支持 1M 上下文"（模型能力）和"实际能跑 1M 上下文"（取决于你的显存）之间的差距**，而框架文档通常只写前者。

**显存不够时的尝试顺序**（代价从低到高）：

```
1. KV 降到 FP8                    ← 代价最低，第一选择
2. 缩短并发 / 减少并发槽位          ← 用并发换长度
3. 加卡并用 TP/PP 扩展容量
4. 最后才考虑 DCP                  ← PCIe 上收益最不确定
```

> DCP（解码上下文并行）在 NVLink 机器上是长上下文的重要手段，但在 **PCIe 机器上收益有限**——ring 传递 KV 的通信开销可能抵消并行收益。

## 七、这份指南最"反潮流"的地方

现在 AI 内容农场很擅长一件事：**把一个看起来合理的数字填进表格**。它们看起来专业，但经不起复现。

所以这个项目做了一个有点固执的约定——**所有结论都带依据标记**：

| 标记 | 含义 |
|---|---|
| **实测** | 有公开可查的测量数据，附硬件、时钟、软件版本与客户端命令 |
| **可推导** | 由硬件规格或框架机制直接推导，不依赖具体某次测量 |
| **待测** | 方向明确但缺公开数据；给出测量方法，等你用自己机器填 |

**我们不做的事：不给没有依据的具体数字。**

本文引用的每一个数字都标了来源和条件；本文没写的部分，不是"忘了写"，而是**目前没有可靠的公开数据**——比如"你的机器上 TP=2 和 TP=4 差多少"，这个只能你自己测。

**空格比编造填得更满有价值。**
