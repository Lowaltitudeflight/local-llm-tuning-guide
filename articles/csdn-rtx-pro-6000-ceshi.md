# 猜 7 个 token 反而比猜 3 个慢 21.7%：4×RTX PRO 6000 无 NVLink 部署实测

> 一台 384 GB 显存的本地推理机，把推测解码的 draft 长度从 3 调到 7——这本该是"更激进的提速手段"，实测吞吐却掉了 21.7%。
> 这不是玄学，是 PCIe 带宽在惩罚你。本文把这台机器上验证过的结论、可以直接抄的配置、和必须会算的显存公式一次讲清。
> **每个数字都标了来源和测试条件**，没有把握的地方我会明说"这个只能你自己测"。

---

## 一、先看这台机器和这个反直觉的数据

测试硬件：**4 × RTX PRO 6000 Max-Q（96 GB GDDR7 ECC，无 NVLink，PCIe 5.0 x16 互联）**

测试条件：TP=4，NVFP4 量化的 MoE 大模型，32 并发槽位，FP8 KV 缓存（来源：Local Inference Lab 的 rtx6kpro 项目，GLM-5.3-Flash 模型页）。

两组推测解码配置的对决：

| 模式 | draft token 数 | C1 单并发 | C8 聚合 | 32K prefill |
|---|---|---|---|---|
| MTP3 | 3 | **281.3 tok/s** | **897.6 tok/s** | 13,816 tok/s |
| DFlash2 K7 | 7 | 229.0 tok/s | 702.6 tok/s | 13,955 tok/s |

**draft 从 3 加到 7，单并发输出下降 18.6%，聚合吞吐下降 21.7%。**

更有意思的是 prefill：两者几乎一样（差 1%）。这符合机制——推测解码只作用于解码阶段。也就是说，**这台机器的 prefill 能力没问题，瓶颈全在解码阶段的通信上**。

> ⚠️ **数据波动提示**：来源自己声明，另一组五次复测中 MTP3 为 265.7–277.0 tok/s、DFlash2 为 212.9–225.2 tok/s，存在约 ±5% 的启动间波动。方向性结论可靠，但不要拿这些数字做精细的版本对比。

如果你看完这一段的第一反应是"啊？猜得多了不是应该更快吗？"——那这篇文章就是为你写的。

## 二、RTX PRO 6000 是张好卡，但它是个"没有 NVLink 的异类"

先把这张卡的特殊性讲清楚。RTX PRO 6000（Blackwell）是目前单卡显存最大的工作站级卡：

| 特性 | 规格 |
|---|---|
| 显存 | 96 GB GDDR7 ECC |
| 互联 | **PCIe 5.0 x16，没有 NVLink** |
| 功耗 | 标准 600W / Max-Q 约 300W 两版 |
| 卡间通信 | 只能走 PCIe，四卡 384 GB 全靠它串起来 |

关键就一句：**这代工作站卡砍掉了 NVLink**。NVIDIA 的数据中心卡（A100/H100/B200）都有 600～1800 GB/s 的 NVLink，而 RTX PRO 6000 的卡间带宽是 PCIe 5.0 x16 的约 128 GB/s——**差 7～14 倍**。

而主流推理框架（vLLM、SGLang 等）的默认参数和"最佳实践"，几乎全是为 NVLink 集群调的。这就是一切问题的根源：

- 照抄"4 卡部署"教程，参数一字不改，吞吐只有别人一半
- 同一批卡，有人跑 1400 tok/s，有人只有 600（后面有这组数据）
- 中文资料里的参数建议互相矛盾，且几乎都不说明测试条件

**带宽差距不是可以忽略的细节，它直接决定哪些配置在你机器上是优的、哪些是最差的。**

## 三、动手调参之前，先跑这一条命令

**这是全文最重要的一段。** 改任何参数之前，先搞清楚你的四张卡到底是怎么连的：

```bash
nvidia-smi topo -m
```

输出是一张矩阵，交叉点就是两张卡之间的连接类型：

```
        GPU0    GPU1    GPU2    GPU3    CPU Affinity    NUMA Affinity
GPU0     X      PIX     PXB     SYS     0-31            0
GPU1    PIX      X      PXB     SYS     0-31            0
GPU2    PXB     PXB      X      SYS     0-31            0
GPU3    SYS     SYS     SYS      X      32-63           1
```

标记含义，按速度从高到低：

| 标记 | 含义 | 相对速度 |
|---|---|---|
| `NV#` | NVLink，数字是链路数 | 最快（PRO 6000 上不会出现） |
| `PIX` | 经过**单个** PCIe Switch | 快 |
| `PXB` | 经过**多个** PCIe Switch | 中 |
| `PHB` | 经过 PCIe Host Bridge（CPU 引出） | 慢 |
| `SYS` | 经过 CPU 间互连（**跨 NUMA**） | 最慢 |

上面这个例子里：GPU0/1/2 在同一组 PCIe Switch 下，GPU3 在另一颗 CPU 上（`SYS`）。此时 `TP=4` 会让每一步 all-reduce 都撞上最慢链路——要出 CPU、过 UPI、再进另一颗 CPU。

**结论当场就有**：TP 不要跨过 `SYS` 和 Switch 边界，宁可改成 `TP=2 × PP=2`。拓扑决定你能选什么，而不是反过来。

## 四、为什么"猜得越多反而越慢"

回到开篇那个 21.7%。推测解码的原理是：草稿模型（或 MTP 头）先一口气猜 N 个 token，主模型一次验证 N 个。猜对了就是白赚，猜错了整批丢弃。在 NVLink 机器上，这套机制近乎稳赚；在 PCIe 机器上，它有三笔隐藏账：

1. **草稿模型要占显存**——挤占 KV 缓存空间，其权重访问还要挤占本就稀缺的带宽
2. **猜错浪费更大**——接受率不变时，draft 越长，单次验证失败丢弃的计算越多
3. **跨卡同步要抢链路**——无 NVLink 的机器上，草稿与验证的同步要和主模型的 all-reduce 争同一条 PCIe

主模型的 all-reduce 本来就在 PCIe 上排队，你再往里塞草稿模型的通信，就是雪上加霜。所以那组数据里验证器速率也印证了：MTP3 是 112.14 steps/s，DFlash2 只有 87.56 steps/s。

**实践建议**：

- 首次配置**从 draft = 2–3 开始测**，不要上来就拉满
- 无 NVLink 多卡场景，draft 保持在 3 左右
- 想提速时，先优化 KV 精度和并行配置，**最后才考虑挂独立草稿模型**

**依据：实测**（单一硬件+模型+量化组合下的测量；"3 一定优于 7"这个具体判断不可迁移到其他组合，但"draft 长度受带宽约束、要从小往大测"这个方法可以）

## 五、并行策略：两条规则 + 一组佐证数据

### 规则 1：能塞进单卡，就别做张量并行

两个独立副本之间**零通信**，吞吐线性叠加；TP 每层都要 all-reduce，在 PCIe 上这个代价会抵消大部分收益。

佐证数据（4 × RTX 3090，无 NVLink，AWQ 量化 35B 级 MoE，vLLM，8K 上下文，128 并发）：

| 配置 | 聚合吞吐 |
|---|---|
| 双实例，各 TP=2 | **1437 tok/s** |
| 单实例，TP=4 | **610 tok/s** |

**2.4 倍差距**，硬件、模型、框架版本全相同，只差并行配置。

### 规则 2：TP 的边界是 PCIe Switch，不是显卡数量

```
能否放进同一 PCIe Switch 下的卡数？
├─ 能  → TP = 该 Switch 下的卡数
└─ 不能 → TP × PP 组合：TP 留在 Switch 内，PP 跨越 Switch
```

原因：TP 的通信发生在**每一层内部**，PP 只在**段的边界**传激活值。层数越深，TP 的累计通信代价越大。

**依据：规则 1 为实测 + 可推导；规则 2 为可推导**（由通信机制直接推导，跨 Switch 走 CPU 内存的路径是 PCIe 体系结构决定的）

## 六、量化：Blackwell 的红利，和必须保护的路由层

RTX PRO 6000 是 Blackwell 架构，原生支持 FP8 和 NVFP4 量化——这是它相对上代卡的真实红利：**96 GB 显存加上 4-bit 权重，能塞进以前必须上数据中心卡的大模型**。

但 MoE 模型有个特殊风险：**路由器选错专家，输出会被彻底带偏**。这个错误是离散的、跳变式的，不会被权重量化的"平均误差"掩盖。公开的量化报告（GLM-5.3-Flash，比较 W4A4 / W4A8 / W4A16 三种激活精度）指向同一结论：**激活量化越激进，MoE 的输出确定性越难保证；把路由器权重保持在高精度，是性价比最高的一步。**

优先级表：

| 优先级 | 做法 |
|---|---|
| 1 | 路由器（router）权重保持 FP32 或至少 BF16 |
| 2 | 专家权重可以更激进量化（NVFP4 / MXFP8） |
| 3 | 激活精度从 A16 起步，确认无损后再降 |

**一个 30 秒的自查项**：同一 prompt 用 greedy 解码跑两次，输出应当**完全一致**。量化后不一致了，说明数值路径出了问题——MoE 上尤其常见。

**依据：实测**

## 七、必须会算的公式：96 GB 到底能跑多长上下文

"我的模型能支持多长上下文"这个问题不需要试错，可以精确估算：

```
每 token 的 KV 字节数 = 2 × 层数 × KV头数 × head_dim × 每元素字节数
                        ↑
                    K 和 V 各一份
```

注意是 **KV 头数**而不是注意力头数——GQA/MQA 模型的 KV 头数远小于注意力头数，这是它省显存的关键。

算例（64 层、8 个 KV 头、head_dim = 128）：

| KV 精度 | 每 token | 32K 上下文 | 128K 上下文 | 1M 上下文 |
|---|---|---|---|---|
| BF16（2B） | 256 KB | 8 GB | 32 GB | 256 GB |
| FP8（1B） | 128 KB | 4 GB | 16 GB | 128 GB |

看最后一行：**即使 KV 压到 FP8，100 万 token 上下文仍需 128 GB**——一张 96 GB 的卡装不下。这就是"模型支持 1M 上下文"（能力）和"你的机器能跑 1M 上下文"（显存）之间的差距，框架文档通常只写前者。

**显存不够时的尝试顺序**（代价从低到高）：

```
1. KV 降到 FP8                    ← 代价最低，第一选择
2. 缩短上下文 / 减少并发槽位        ← 用并发换长度
3. 加卡并用 TP/PP 扩展容量
4. 最后才考虑 DCP                  ← PCIe 上收益最不确定
```

**依据：公式为可推导（直接由模型结构计算）；DCP 结论为实测 + 可推导**

## 八、直接能抄的配置：4 × 96 GB

**先看拓扑，再选 A 或 B**（配方已收录在仓库 `recipes/4x-96gb-pcie.md`）：

### 情况 A：四卡在同一 PCIe Switch 组（TP=4）

```bash
vllm serve <your-model> \
  --tensor-parallel-size 4 \
  --pipeline-parallel-size 1 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --max-num-seqs 32 \
  --max-num-batched-tokens 4096 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --host 0.0.0.0 --port 8000
```

### 情况 B：四卡分属两个 Switch（TP=2 × PP=2）

```bash
vllm serve <your-model> \
  --tensor-parallel-size 2 \
  --pipeline-parallel-size 2 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --max-num-seqs 32 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --host 0.0.0.0 --port 8000
```

**两个容易翻车的细节**：

- `--gpu-memory-utilization` **不要一上手就 0.95**，突发峰值容易 OOM，0.90 起步
- 如果你的卡是 Max-Q 版（约 300W），**功耗墙可能先于显存成为瓶颈**——测出来的数字一定要标注功耗上限，否则别人复现不了

## 九、这篇文章最"反潮流"的地方

AI 内容农场很擅长把一个看起来合理的数字填进表格。所以本项目立了一条固执的规矩——**所有结论都带依据标记**：

| 标记 | 含义 |
|---|---|
| **实测** | 有公开可查的测量数据，附硬件、时钟、软件版本与客户端命令 |
| **可推导** | 由硬件规格或框架机制直接推导，不依赖某次具体测量 |
| **待测** | 方向明确但缺公开数据；给出测量方法，等你用自己机器填 |

**我们不做的事：不给没有依据的具体数字。** 空格比编造填得更满有价值。
